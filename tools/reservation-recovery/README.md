# 예약 자동반영 수신과 복구

이 패키지는 기존 Mac의 격리된 Hermes/Kakao 런타임에 설치한다. GAS, 예약 시트 구조,
결제 데이터, 모델, 역사적 작업 보류 매니페스트는 변경하지 않는다.

## 보장 범위

- 수신 전용 카카오 `전체 상담` 목록을 유지한다. 검색/서류 발송 화면과 분리한다.
- 웹훅 성공 응답 전에 원문을 파일·디렉터리 fsync까지 보관한다. 외부 DB 지연은 수신 ACK를 막지 않는다.
- 재시작 후 같은 원문·작업을 이어받고, 이미 존재하는 정확한 Gateway 작업은 재실행하지 않는다.
- 수신 복구 경로의 원문 조회 동시 실행은 1개, Native AI 작업 동시 실행은 2개로 제한한다.
- 새 상담을 우선하고 과거 대조는 제한된 속도로 진행한다. 실패 작업이 원문 대기열을 영구 독점하지 않는다.
- 과거 목록을 스크롤하는 동안 일반 새 메시지 감지를 잠시 억제한다. 복귀 후 실제 새 메시지를 다시 감지한다.
- 카카오의 삭제 메시지 안내를 실제 대화 문장으로 오인하지 않는다. 실제 예약 문장은 원문 일치를 계속 요구한다.
- 정상 종료 뒤 TCP TIME_WAIT를 실행 중인 서버로 오인하지 않는다. 실행 중 포트와 서비스 소유권은 계속 보호한다.
- 직접 만든 정확한 탭만 일시정지를 해제한다. 기존 탭/다른 URL/작성 중 메시지는 건드리지 않는다.
- 14일 목록 스캔이 과거 날짜 경계에 도달하고 모든 수신 ACK를 받은 경우에만 범위 확인을 기록한다.
  장기 중단 뒤에는 마지막 성공 시점까지 대조 기간을 늘린다.
- 도구 실행·저장 증거가 전혀 없는 실패와 적용 시작 전 무효 AI 응답만 새로운 안정된 재시도 ID로 재확인한다. 재시도 횟수와 지연을 원문에 보관하고 최대 2번으로 제한한다.
  저장 불확실/부분 성공/기존 거래의 결과는 원장 대조 없이 다시 쓰지 않는다.
- 시스템 장애는 기존 슬랙 단톡방에 묶어 알린다. 실패 고객별 DM 폭주 경로는 중단한다.
  일반 견적·가격 처리 알림은 유지한다. 증상이 조금 바뀌어도 장애 알림은 15분 간격을 두며,
  동일 상태는 반복 발송하지 않는다. 2회 연속 이상/3회 연속 정상으로 순간적인 흔들림을 구분한다.

**목록 수신 완료는 예약 대조 완료가 아니다.** `review_required`와 대기 수는 수신 기록 수이며
예약 누락 확정 건수가 아니다. 저장 결과 대조 대상과 원문은 보존하며 자동으로 누락 확정 처리하지 않는다.
로그인/인증이 만료되면 알리고 사용자의 정상 인증을 기다린다. 실행 중인 업무를 무조건 종료하지 않는다.

## 설치와 버전 고정

```sh
python3 tools/reservation-recovery/install.py --root /absolute/isolated/runtime
```

설치 전 현재 환경·런타임·활성화 매니페스트 해시를 확인하고, 변경할 파일과 매니페스트를
`control/automatic-recovery-YYYYmmdd-HHMMSS/`에 백업한다. 설치 오류는 기존 파일과 매니페스트로
복원한다. Native adapter 패치는 forward 방식으로 한 번만 적용하며 반복 설치가 이를 되돌릴 수 없다. 기존 활성화 gates와 역사적 hold 파일은 유지한다. 공유 파일의 모든 서비스 핀을 갱신한다.

설치기는 서비스를 강제로 재시작하지 않는다.

```sh
/isolated/runtime/venv-root/bin/python tools/reservation-recovery/release.py --root /absolute/isolated/runtime
```

배포 도구는 Hermes의 기존 외부 drain 기능으로 새 턴 수락을 잠시 보류하고 해당 Native 업무와 적용 작업이 유휴 상태가 되기를 기다린다. 독립적인 Slack 업무는 계속 진행한다. 실행 중인 AI에 종료 신호를 보내서 끝내지 않는다. Native worker의 정상 종료와 활성 업무 종료를 확인한 뒤
bridge를 재시작하고 worker의 launchd 자동 실행을 다시 활성화한다. watcher는 독립적으로 재시작 가능하다.
feature 브랜치에서 GAS 배포 스크립트를 실행하지 않는다. 이 패키지는 격리된 런타임만 갱신한다.

설치 후 `control/runtime.json`의 watcher argv는 `control/reservation-recovery/supervisor.py`를 가리킨다.
Chrome 서비스는 기존 launcher를 유지한다. 기존 프로세스 소유권, 환경, 정확한 커맨드, 프로세스 생성
시각 검증을 완화하지 않는다.

## 운영 상태

- `state/watcher-supervisor.json`: 현재 전용 수신, 전체 상담 범위, bridge/worker 연결, 스캔 상태
- `state/reservation-coverage.json`: 마지막 ACK까지 확인된 대화 목록 스캔 범위
- `state/reservation-recovery.json`: 지속된 장애, 알림 결과, 헤이빌리 업무 ID
- `production-runtime/tools/kakao-dom-bridge/queue/durable-intake-status.json`: 원문 전달·대기·대조 수
- `.../queue/durable-intake/*.event.json`: 보관 원문. 수납/예약 완료의 증거로 쓰지 않는다.
- `.../queue/durable-intake/*.handoff.json`: 다음 보관소로 전달했다는 검증된 증거
- `control/reservation-recovery-notifications.json`: 기존 슬랙 채널 ID. 인증 토큰은 기존 env에만 둔다.
- `control/reservation-recovery-control.json`: `pauseBackfill: true`면 과거 스캔/새 과거 원문 조회만 보류한다.
  새 문의는 계속 받는다. 보류 원문은 삭제하지 않는다. false로 돌리면 속도 제한 하에 이어간다.

단톡방의 남은 대조 현황 알림과 실제 수신/처리기 장애 알림을 구분한다. 헤이빌리 후속조치에는
한 개의 지속적인 복구 사례로 표시하고, 대기 기록 수와 대조 고객 예시를 제공한다.

## 검증

```sh
./tools/reservation-recovery/run-tests.sh /absolute/isolated/runtime
```

실제 설치된 통합 코드를 읽어 격리된 테스트 저장소와 가짜 전송을 사용한다.
운영 예약 쓰기, 고객 발송, GUI 호출을 테스트에서 수행하지 않는다.
원문 fsync 실패·충돌·크래시 구간·중복·저장 불확실·대기열 공정성·동시 수신 폭주·과거 스크롤·
중단 재처리·정확한 소유 탭의 로딩 정지·알림 폭주를 확인한다.

실행 중 프로세스의 실제 재기동, 새로운 Gateway 작업 완료, 장부/앱 읽기와 슬랙 수신은 별도 운영
검증이다. 테스트 통과나 소스 배포만으로 실제 예약 대조 완료라고 보고하지 않는다.

## 장애별 동작

| 상황 | 복구와 확인 |
| --- | --- |
| watcher 프로세스 종료 | launchd 재기동 후 실제 전체 상담 읽기 확인 |
| 전용 수신 탭 누락/변경 | 정확한 새 전용 탭 생성, 다른 직원 탭은 보존 |
| 검색 상태가 수신을 가림 | 전용 전체 상담 목록으로 독립 복구 |
| 로딩 전에 멈춘 새 원문 탭 | 생성 영수증으로 소유권을 입증한 탭만 재개 |
| 외부 DB 실패 | 원문 보관 후 ACK, 보관 원문에서 제한된 재처리 |
| bridge/worker 실제 종료 | 기존 launchd 소유권·버전 검증 후 재시작 |
| worker 연결 끊김 | 확인된 소유 프로세스가 유휴 상태일 때만 재시작 |
| 이미 업무가 실행 중/저장 결과 불명 | 원문과 operation fence 보존, 원장 대조 대상으로 표시 |
| 인증 만료 | 단톡방·앱에 알림, 정상 로그인 필요 |
| 디스크 부족/원문 손상 | 성공 ACK 금지, 알림, 원문 삭제나 임의 축약 금지 |
| 장애 중 들어온 원문 | 부팅 후 raw-event 슬롯을 보장해 복구 |
| 과거 재점검 유입 증가 | 원문 조회 1개 제한, 최신 문의 우선, 과거 복구 속도 제한 |
| 실패 알림 증가 | 개별 장애 DM 대신 묶음 알림, 원문·개별 실패 증거 보존 |

## 되돌리기

정확한 설치 백업의 파일과 `runtime.json`, `ACTIVATION.json`을 함께 검토해 되돌린다.
다른 세션이 이후 수정한 파일을 무조건 덮어쓰지 않는다. 원문 journal과 예약/결제 자료는 삭제하지 않는다.
이전 bridge로 되돌렸다면 신규 journal을 읽지 않을 수 있으므로 복구 완료로 표시하지 않는다.
보존된 원문을 현재 코드로 재대조하거나, 결과 확인된 작업의 정확한 영수증과 연결한다.

# 기본 단가·신규 품목·신규 장비 등록 후 견적 이어가기

기존 Slack 스레드에서 평소처럼 대화한다. 사장에게 명령어, 태그, JSON, 특별한 답변 형식을 요구하지 않는다. 거래별 무료·할인을 상시 단가나 새 보유 재고로 만들지 않는다. 이미 검증된 정보는 재질문하지 않는다.

## 기본 일단가만 빠진 기존 품목

정확한 세트마스터 품목명으로 “폴리 1개 하루 기본 단가 얼마로 등록할까요?”처럼 묻는다. 사장이 같은 스레드에서 “5,000원”이라고 답하면 `village_master_price`에 품목명과 숫자 단가를 전달한다. `question_ts`는 명확한 직전 질문을 가리킬 때만 전달한다. 원문 작성자·봇·단위·스레드 검증은 도구가 수행한다. 기존 단가가 0이면 빈칸으로 취급하지 않는다. 기존 값과 다른 금액은 교체 확인 없이 덮어쓰지 않는다.

## 세트마스터에 없는 신규 품목

현재 세트마스터와 장비마스터·재고 원장을 먼저 조회한다. 품목 이름과 구성 장비별 수량을 확정한다. 단품이면 구성은 해당 장비 1개다. 기존 장비·별칭과 동일한 실물을 새 재고로 중복 등록하지 않는다. 구성이나 신규 재고 수량이 불명확할 때만 그 빠진 사실을 자연스럽게 묻는다.

구성이 확인되면 질문에 새 품목과 구성을 명시한다. 예: “인터뷰 세트 세트마스터에 새 품목으로 등록하겠습니다. 구성은 소니 A7S3 1개, NP-FZ100 3개입니다. 1개 하루 기본 단가 얼마로 등록할까요?” 사장은 “50,000원”처럼 금액만 답하면 된다. 헤이빌리는 이 답을 앞선 계획에 연결해 `village_master_create(target, price, components)`를 호출한다. 이미 있는 장비에는 `new_equipment`를 넣지 않는다.

## 장비마스터에도 없는 완전 신규 장비·재고

신규 실물 장비별 정확한 이름·대분류·카테고리·총보유수량·정비중수량을 확인한다. 렌탈 수량을 총보유수량으로 대체하지 않는다. 정비중 0도 모르면 추측하지 않는다. 마지막 기본 단가 질문에 확인한 재고 계획을 함께 명시한다.

예: “폴리 세트마스터에 새 품목으로 등록하겠습니다. 구성은 폴리 1개입니다. 신규 재고는 폴리(대분류 기타, 카테고리 기타, 총보유 2개, 정비중 0개)입니다. 1개 하루 기본 단가 얼마로 등록할까요?”

사장은 “5,000원”만 답하면 된다. `village_master_create`의 `components`는 `[{name:'폴리',qty:1}]`, `new_equipment`는 `[{name:'폴리',major:'기타',category:'기타',stockTotal:2,stockMaintenance:0}]`이다. 여러 신규 장비는 질문의 `신규 재고는` 부분에서 `; `로 구분해 각각 명시한다. 이 명세는 헤이빌리가 질문을 구성하기 위한 것이며 사장에게 특정 형식을 요구하는 규칙이 아니다.

도구는 사장 원문을 직접 검증한 후 기존 원장 RPC로 신규 장비·재고를 등록하고, 장비마스터 미러를 확인한 뒤 세트마스터·목록·계약 템플릿·신규 실사 항목을 반영하고 재조회한다. 재고 원본은 `equipment_ledger`다. 일반 시트 쓰기로 원장을 우회하지 않는다. 카테고리와 수량을 확인하지 않은 새 장비를 임의로 만들지 않는다.

## 결과와 원래 업무 재개

`status=verified|already_verified`와 `downstreamSync=verified`를 확인한 뒤 저장해 둔 원래 견적을 이어간다. 해당 요청·거래의 최신 취소/등록 상태와 구성·할인유형을 재조회한다. 잘못 펼쳐진 기존 요청은 승인된 기존 요청 수정 절차로 복구하고 전체 요청 그룹을 확인한다. 취소된 예약을 되살리거나 새 예약을 중복 생성하지 않는다. 고객 발송·예약 확정의 기존 승인 규칙은 그대로 적용한다.

`inventory_saved_catalog_pending`이면 재고가 저장됐거나 저장 여부 확인이 필요한 상태다. 신규 장비부터 다시 만들지 말고 같은 원문·도구 인자로 재시도한다. `master_saved_sync_pending`이면 마스터 저장은 됐지만 목록·템플릿·실사 동기화가 미완료다. 두 경우 모두 견적을 완료로 보고하지 않는다. 중복 요청은 원문 기반의 같은 작업 ID로 복구하며, ID를 바꿔 잠금이나 이력을 우회하지 않는다.

`needs_review`이면 원문과 현재 마스터를 확인해 불명확한 사실 하나만 묻는다. 직원·고객 답변, 수정된 메시지, 여러 질문 사이의 짧은 답변, 이후 사장 정정/취소는 자동 승인으로 사용하지 않는다. 예전 일반적인 “이번 폴리 얼마?”는 상시 단가가 불명확하므로 한 번만 구분한다. 메모리 저장은 마스터/원장 저장의 증거가 아니다.

root에서 현재 사장 Slack 턴에만 호출한다. worker에 도구가 없으면 사장의 원문·스레드 ID를 root에 넘기고 직접 `verifiedOwner`를 만들어 쓰거나 standalone CLI로 대체하지 않는다. 죽은 프로세스가 남긴 `.lock`은 자동 삭제하지 않고 실행 프로세스·준비 요청·서버 이력과 실제 값을 먼저 대조한다.

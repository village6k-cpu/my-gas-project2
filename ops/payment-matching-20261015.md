# 2026-10-15 결제 자동매칭 복구 및 금액 변경 대안

## 확인한 장애

- Village Finance의 Toss 웹훅은 승인 원본을 먼저 저장한 다음 GAS를 조회·갱신한다.
- 운영 요청 로그에서 10월 10일과 14일 `Task timed out after 30 seconds`를 확인했다. GAS HTTP 호출의 개별 타임아웃은 40초이고 조회와 갱신이 순차로 필요하므로 서버 제한과 맞지 않았다.
- 기존 중복 이벤트 처리는 원본 존재 여부만 확인하고 종료했다. 원본 저장 이후 장부 반영 전에 중단된 이벤트가 다시 들어와도 복구하지 못했다.
- Toss Front 예약 결제 confirm API도 GAS의 HTTP 200 본문에 담긴 실패를 검사하지 않아, 실제 장부 실패를 성공으로 반환하고 단말의 재시도 기록을 지울 수 있었다.
- 실제 운영 대사에서 전체 대시보드 검색이 40초를 초과했다. 캐시가 채워진 뒤에는 같은 조회가 18.72초에 성공했으므로, 서버 제한만 늘려서는 조회 지연 자체가 해결되지 않는다.
- `updateTradePaymentMethod`는 장부 변경 후 Supabase dirty 표시를 하지 않았다. 복구 건의 거래내역 M열은 입금완료인데 화면용 `village.trades.deposit_status`는 NULL인 상태를 직접 확인했다.
- 입금매칭 `matchDeposits`는 10월 15일 13:33:41, 13:48:41 KST 정상 종료. 13:48 로그는 대기행 671, 입금거래 313, 매칭 0이다. 실행·계좌조회 경로는 살아 있지만 모든 입금이 매칭된다는 의미는 아니다.

## 적용 범위

- Finance 웹훅 함수 실행 상한을 180초로 맞춘다.
- 원본과 별도로 장부 처리 결과·처리 중인 거래ID를 저장한다. 오류는 재전송 가능한 503으로 반환하고, 재전송 시 같은 거래에만 재시도한다. 동시 요청은 상태 비교와 처리 기한으로 보호한다.
- 배포 이전 이벤트는 `legacy`로 보존하며 임의로 전체 재실행하지 않는다.
- 저장된 서명 검증 승인에 대한 진단/복구 API를 추가한다. 기본값은 읽기 전용이며, 실제 반영은 진단에서 확인한 거래ID가 필요하다. 취소된 결제는 제외한다.
- 환불·부분입금은 금액만으로 자동 완납 처리하지 않는다.
- Toss Front confirm은 `success=true`와 `wroteSheet=true`를 모두 확인해야 성공한다.
- 카드 후보 전용 내부 API는 거래내역의 현재 I열 금액과 계약마스터 E/G열 대여일을 직접 읽는다. 대시보드/장비 전체 검색과 150행 검색 제한을 제거한다.
- GAS 결제 변경 후 기존 1분 Supabase 동기화 큐에 거래를 표시한다. 카드 후속값 K/L/M을 쓰지 못하면 성공을 반환하지 않는다.
- Google Sheets 구조 및 계좌입금 트리거 주기는 변경하지 않는다.

## 금액 차이 대안

권장안은 결제 원본과 청구 금액을 거래ID로 연결하고 각각 보존하는 것이다. 단순히 ±몇 원 또는 ±몇 %를 자동 승인하면 같은 금액의 다른 고객, 부분납, 합산납, 환불을 구분할 수 없다.

| 상황 | 처리 원칙 |
| --- | --- |
| 현장 장비 추가·제외 | 거래ID를 유지하면서 최종 청구액과 변경 이력을 기록. 결제 직전 최신 금액을 다시 읽기 |
| 예약 선택 카드결제 | 거래ID와 승인 식별자를 직접 연결. 정확 금액 검색은 보조 경로로만 사용 |
| 금액 직접 카드결제 | 결제 전 예약 선택 또는 결제 후 승인내역과 예약 연결 절차 제공 |
| 일부 입금 / 추가금 | 기존 수납액을 덮지 않고 결제 내역을 누적. 최종 청구액에서 수납액을 빼 잔액 산출 |
| 여러 예약 합산입금 | 입금 한 건을 여러 거래에 배분하고 배분합이 원본 입금액을 넘지 않게 제한 |
| 과입금 | 실제 수납액과 초과분을 함께 보존하고 환불/차감 확인 대상으로 표시 |
| 이름 차이 / 같은 금액 여러 건 | 후보·금액 차이·입금 시각을 운영 화면에 표시하여 확인 후 연결 |

즉시 권장하는 다음 작업은 직원용 대시보드의 미매칭 결제함이다. 각 결제의 원본 승인/입금 ID, 금액, 시각, 연결 후보, 차액, 처리 상태를 보이고 확인된 연결만 저장한다. 그 다음 수납 배분 원장을 추가해 합산·부분입금과 변경 후 잔액을 처리한다.

현재 계좌매칭은 이름 포함 + 단일 금액 일치이며 사용한 입금의 식별자를 실행 간 영속 보관하지 않는다. 따라서 반복되는 동명·동액 거래의 오매칭 방지까지 완료된 것으로 보아서는 안 된다. 은행 거래 고유번호와 거래ID별 배분을 보관하는 개선이 필요하다.

확인한 예외 사례: 36,960원 한 번 입금과 18,480원 예약 두 건(`261004-006`, `261004-007`), 52,000원 입금과 52,800원 청구(`261014-012`). 전자는 합산 배분 확인, 후자는 800원 잔액 또는 청구액 정정 확인이 필요하다. 임의로 완납 처리하지 않았다. 현행 은행 매칭은 장부 M열만 변경하므로 화면용 Supabase 상태 전달까지 별도 개선 대상이다.

## 검증

- Finance 전체 테스트와 카드/웹훅 집중 테스트 실행.
- Toss confirm 실패 응답 회귀 테스트는 수정 전 코드에서 HTTP 200을 반환하며 실패하고, 수정 후 502로 통과한다.
- Finance 전체 테스트 433개 통과. 후속 후보 조회/승인 응답 변경 후 집중 테스트 44개 통과.
- GAS 후보 조회 10개 검사, 결제 dirty 표시/부분 실패 검사, Toss confirm 8개 검사 통과. 기존 결제취소 동작·취소 API·CORS·입금상태·결제옵션 회귀 검사도 통과.
- 은행 GAS 원본을 별도 임시 디렉터리에 pull하여 `matchDeposits`와 입금 조회 함수가 검토한 로컬 코드와 같음을 확인했다.
